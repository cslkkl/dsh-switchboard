# 决策：配置写入必须保留未提及字段（2026-10-20）

状态：生效

## 问题

`POST /api/v1/switchboard/rules` 用 `effectiveSettings(config)` 拼出一个 6 键对象
（`enabled` / `rules` / `members` / `defaultRoute` / `maxDepth` / `applyToFork`），
然后 `writeJsonFile` **整体覆写** `rules.json`。

`effectiveSettings` 实际产出 9 个键，多出的三个恰好是写入时被丢掉的：

| 丢失键 | 落点 | 症状 |
|---|---|---|
| `sessions` | 「本对话默认」 | 保存设置后对话默认消失，退回继承 |
| `asked` | 已询问标记 | 下次派活重新弹一次询问 |
| `askOnFirst` | 询问开关 | 无论文件里设成什么，保存后一律回到默认 `true` |

复现路径：对话里首次派活 → 回答「本对话默认」→ 插件写 `sessions` + `asked` →
打开插件详情页改任意一项（哪怕只改 `maxDepth`）→ 点保存 → 两张表被清空 →
同一对话再次派活，又被问一次。用户视角是「保存即清空本对话默认」。

根因不在合并逻辑，而在**写入源选错**：拿归一化视图当磁盘形态用。归一化会
（1）只保留已知键，（2）把 patch 里的值烘进结果，（3）丢掉 `asked` 的原始语义。

## 决策

**所有写路径一律 `{ ...原文件, ...本次改动 }`，不得整体覆写。**

具体三条：

1. **写入前另读原始文件**：`const raw = readJsonFile(rulesPath()) ?? {}`。
   不用 `effectiveSettings()` 当写入基底——它没有「文件里还剩哪些键」这个概念。
2. **改动集只含本次真正要改的键**：`POST /rules` 收敛为 7 个键
   （6 个旧键 + `askOnFirst`），`sessions` / `asked` 归 `/session` 独占，
   其余键和未来新增键随 `...raw` 原样透传。
3. **写入语句固定形状**：`writeJsonFile(rulesPath(), { ...raw, ...merged })`。
   全仓已对齐此形状的路径：`/rules`、`/member`、`/bulk`、`/session`、
   首次询问的 `asked` 记账。

配套校验：`maxDepth` 走 `asMaxDepth` 而非 `Number.isSafeInteger`，
负数（手填 `-1` 会跳过全部子代）按非法值丢弃、保留当前值。

## 替代方案（强制）

- **按字段存在性合并，但只写已知键**：现有的「`'key' in body` 才算要改」这套
  语义正确，问题出在输出侧。只写白名单键仍会在每次保存时抹掉 `raw` 里的
  未知键；每加一个字段都要同步改写入白名单，漏一处就是同一个 bug 的第二季。
  `...raw` 把「未知键」变成免费能力，新增字段不必再改写入路径。

- **每次全量提交（前端持有完整配置）**：要求设置卡片持有 `sessions` / `asked` /
  `askOnFirst` 三份它并不编辑的数据，并保证任何一次保存都原样带回。三个问题：
  多标签页并发时后写者用陈旧快照覆盖先写者；`sessions` / `asked` 是宿主在
  派活过程中**自己写**的，前端持有的副本天生落后；将来任何不经 UI 的写入
  （`/spawn` 预写点名表）都会与前端副本互相踩。写入方的隔离性比提交完整性更值钱。

- **继续用 `effectiveSettings()` 当写入基底，只补三个键**：能掩盖当前症状，
  但 patch 里的值会被烘进 `rules.json`，从此反过来盖住以后对 patch 的修改
  （文件优先 + 烘焙值 = patch 永远失效）。归一化视图与磁盘形态必须分开。

## 影响

- 收益：保存设置不再有副作用；`askOnFirst` 第一次成为真正可写的字段；
  新增配置字段默认具备「旧文件不丢」的向后兼容。
- 代价：写入路径多一次 `readJsonFile`（同步、小文件，可忽略）；
  `raw` 里可能留存已被删除字段的历史残值，需要显式清理而不是自然淘汰。
- 已知坑一：`...raw` 保留未知键，也保留**手写进文件的非法值**。
  `effectiveSettings` 读取时仍会归一化它们，所以不会立刻出错，
  但磁盘上与生效值可能不一致，排查时要看两处。
- 已知坑二：`spawnChild` 的队友分支（预写点名表）仍以
  `{ ...effectiveSettings(), members: {...} }` 落盘，会丢未知键并把 patch 值烘焙进文件。
  与本节决策不一致，属遗留项，待单独收敛。
- 已知坑三：本条只约束「写不覆盖」。`asked` 的值是时间戳字符串，
  不能按路由对象校验——见 [首次询问决策](2026-10-20-session-default-ask.md)。
